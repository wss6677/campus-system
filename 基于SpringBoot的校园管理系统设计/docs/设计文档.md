# 加利顿大学 · 校园公告管理系统 设计文档

> 一句话定位：把「发通知」这件小事，做成一套有组织层级、有审批责任链、有触达回执、有数据沉淀的校园信息中枢。
> 交付物：本设计文档 + 高保真 HTML 原型（`prototype/campus-pulse.html`）+ 可编译 SpringBoot 后端（`backend/`）。

---

## 一、世界观设定（Worldview）

### 1.1 背景

**加利顿大学**是一所三校区（**本部·加利顿南苑**、**东湖校区**、**北岭校区**）的综合性大学，下设 8 个学院、3 个直属部门（信息中心、学生工作部、后勤保障处）。过去通知靠 QQ 群、微信群、纸质张贴，导致：

| 痛点 | 后果 | 系统对策 |
|---|---|---|
| 通知多头下发，无统一出口 | 学生漏看、重复看 | 统一公告中心 + 分类订阅 |
| 谁能发全校通知没有边界 | 误发、越权发布 | 组织层级 + 角色矩阵 + 审批链 |
| 发了不知道谁看了 | 紧急通知无法追责、无法催办 | 阅读回执 + 未读催办 + 部门未读排行 |
| 历史通知无处可查 | 评奖、审计、追溯无据 | 全文检索 + 版本快照 + 操作审计 |
| 红头文件与网络通知两张皮 | 格式不统一 | 红头文件模板 + PDF 导出 |

### 1.2 组织与角色（六角色十二能力）

```
加利顿大学
├── 信息中心（校级技术主管）        → SUPER_ADMIN 系统管理员
├── 党委宣传部（校级审核出口）      → UNIV_AUDITOR 校级审核员
├── 计算机学院
│   ├── 学院办公室                 → DEPT_PUBLISHER 院系发布员
│   ├── 教研室 / 教师              → TEACHER 教职工
│   └── 2023 级软件工程 1 班        → STUDENT 学生
└── 学工部 / 后勤保障处 / 图书馆 …  → DEPT_PUBLISHER / TEACHER
```

| 角色 | 角色码 | 数据范围 | 核心能力 |
|---|---|---|---|
| 系统管理员 | `SUPER_ADMIN` | 全部 | 组织/用户/角色/分类/敏感词/模板/审计/系统配置 |
| 校级审核员 | `UNIV_AUDITOR` | 全部 | 审核所有院系公告、撤回、归档、置顶、横幅 |
| 院系发布员 | `DEPT_PUBLISHER` | 本部门 | 起草、提交、发布本部门公告、查看本部门回执 |
| 教职工 | `TEACHER` | 全校可见范围 | 阅读、评论、订阅、下载附件、查看回执统计 |
| 学生 | `STUDENT` | 全校+本院+本班 | 阅读、评论、订阅、签到式回执 |
| 访客 | `GUEST` | 仅公开公告 | 只读 |

**权限模型**：RBAC（角色）+ 数据范围（`ALL / COLLEGE / SELF`）+ 公告可见范围（`ALL / COLLEGE / CLASS / CUSTOM`）三层叠加。可见范围与数据范围取交集，这是本系统最容易被忽略、也最能体现"完整度"的地方。

### 1.3 公告生命周期（状态机）

```
                    ┌──────────── 驳回 ─────────────┐
                    ▼                               │
  ┌────────┐ submit ┌─────────┐ audit 通过  ┌──────────────┐
  │ DRAFT  │───────▶│ PENDING │────────────▶│  PUBLISHED   │──┐
  │ 草稿    │        │ 待审核   │             │  已发布       │  │ expireTime 到期
  └────────┘        └─────────┘             └──────────────┘  ▼
      ▲  分类 needAudit=0（免审）自动通过           │        ┌──────────┐
      │                                          │withdraw│ ARCHIVED │
      │                                          ▼        │  已归档   │
      │                                    ┌───────────┐  └──────────┘
      └──────── 重新编辑 ───────────────────│ WITHDRAWN │
                                           │  已撤回    │
  未来时间审核通过 ──▶ SCHEDULED(定时发布) ──每分钟扫描──▶ PUBLISHED
```

### 1.4 公告分类（六类，各自不同的默认策略）

| 分类 | 颜色 | 默认审批 | 默认回执 | 典型场景 |
|---|---|---|---|---|
| 行政通知 | 加利顿蓝 | 需要 | 需要 | 放假安排、校历调整 |
| 教务教学 | 墨绿 | 需要 | 需要 | 选课、考试、成绩 |
| 科研动态 | 紫 | 需要 | 否 | 项目申报、学术报告 |
| 活动预告 | 橙 | 免审 | 否 | 讲座、社团、比赛 |
| 安全提醒 | 红 | 需要 + 强制推送 | 需要 | 消防、防诈、极端天气 |
| 招标采购 | 灰蓝 | 需要 | 否 | 采购公告、中标公示 |

### 3.2 接口清单（约 60 个 REST 端点，节选）

```
POST   /api/auth/login                     登录 → {token, user}
GET    /api/announcement/page              分页查询（含数据范围裁剪）
POST   /api/announcement/save              保存草稿
PUT    /api/announcement/{id}              编辑（自动生成版本快照）
POST   /api/announcement/{id}/submit       提交审核
POST   /api/approval/{id}/audit            审核（通过/驳回 + 意见）
POST   /api/announcement/{id}/publish      立即发布（生成回执 + 推送 + 站内信）
GET    /api/receipt/stat/{announcementId}  回执统计（总人数/已读/未读/部门排行）
POST   /api/receipt/urge                   一键催办未读
GET    /api/stats/overview                 看板概览（Redis 缓存 60s）
GET    /api/stats/trend?days=30            发布趋势
GET    /api/dept/tree                      组织树
POST   /api/file/upload                    附件上传（白名单校验）
```

### 3.3 安全设计

- JWT（HS256，`campus.jwt.secret`）无状态鉴权，`AuthInterceptor` 统一解析并写入 `ThreadLocal`。
- `@RequireRole({"SUPER_ADMIN","UNIV_AUDITOR"})` 方法级角色校验，越权返回 403。
- 富文本 XSS 过滤 + 附件扩展名白名单（`doc,docx,pdf,xls,xlsx,ppt,pptx,jpg,png,zip`）+ 大小上限 20MB。
- 敏感词三级处理：命中 `BLOCK` 阻断提交，命中 `WARN` 提示但不阻断；所有命中记入审计。
- 关键写操作（发布/撤回/审核/删除）全量入 `ann_approval_log` 与 `sys_operation_log`，可回溯到人。

## 四、制作步骤（从 0 到可演示，共 6 个阶段）

### 阶段 0 · 环境（30 分钟）
```bash
java -version      # 需要 JDK 21
mvn -v             # 需要 Maven 3.9+
mysql --version    # 需要 MySQL 8（或改用 H2 本地演示）
redis-cli ping     # 需要 Redis 7（可先注释掉，用内存缓存替代）
```

### 阶段 1 · 建库建表 + 种子数据（0.5 天）
```bash
mysql -uroot -p123456 < backend/src/main/resources/db/schema.sql
mysql -uroot -p123456 < backend/src/main/resources/db/data.sql
```
校验：`select status, count(*) from ann_announcement group by status;` 六个状态都有数据。

### 阶段 2 · 后端骨架跑通（1 天）
```bash
cd backend
mvn clean package -DskipTests
java -jar target/campus-announcement-1.0.0.jar
# 打开 http://localhost:8080/doc.html 查看 Knife4j 接口文档
```
验收：`GET /api/auth/login` 用 `admin / 123456` 拿到 token；`GET /api/announcement/page` 带 token 返回分页数据。

### 阶段 3 · 核心业务闭环（2 天，按顺序做，每步都可独立验收）
1. **公告 CRUD** → 用 Swagger 建一条草稿，`GET /{id}` 能读到，浏览量 +1。
2. **审批流** → `submit` 后状态变 `PENDING`，`audit` 通过后变 `PUBLISHED`，`GET /api/approval/timeline/{id}` 有完整链路。
3. **可见范围** → 换 `STUDENT` 账号登录，只能看到 `PUBLISHED` 且命中本院的公告（数据范围裁剪）。
4. **阅读回执** → 学生调 `POST /api/receipt/read/{id}`，发布员调 `GET /api/receipt/stat/{id}` 看到未读排行；`POST /api/receipt/urge` 后学生站内信 +1。
5. **定时发布** → 建一条 `publishTime = now + 2min` 的公告并审核通过，等 2 分钟自动变 `PUBLISHED`（看日志里的定时任务输出）。
6. **统计看板** → `GET /api/stats/overview` 返回 11 个指标，连续两次调用第二次明显更快（Redis 命中）。

### 阶段 4 · 前端落地（2 天）
- 方式 A（推荐毕业设计/课设）：把原型 `prototype/campus-pulse.html` 的界面结构直接搬到 Vue3 + Element Plus（`vite + vue-router + pinia + axios + echarts`），原型里每个卡片/表格/图表都对应一个组件。
- 方式 B（快速演示）：保留单文件 HTML，把 `MOCK` 数据层替换为 `fetch('/api/...')`，加 `localStorage` 存 token，即可成为真实可用前端。
- 方式 C（零前端）：Spring Boot 集成 Thymeleaf，用 `index.html` 模板直出，最省事但交互弱。

### 阶段 5 · 加分项（选做，答辩很吃这一套）
全文检索（Elasticsearch / MySQL 全文索引）、导出红头文件 PDF（iText）、企业微信/钉钉机器人 Webhook、公告阅读完成率排行、多校区数据权限隔离、操作日志大屏、Docker Compose 一键部署。

### 阶段 6 · 交付
```bash
mvn clean package                       # 产出可执行 jar
docker build -t campus-pulse:1.0.0 .    # 可选
```
交付物：源码 + `schema.sql`/`data.sql` + 接口文档（Knife4j）+ 本设计文档 + HTML 原型 + 演示账号表。

## 六、验收清单（12 条，答辩自查）

1. 六种状态在数据库里都能复现，且状态流转写过审批日志。
2. `DEPT_PUBLISHER` 看不到别的学院草稿；`STUDENT` 看不到任何非已发布公告。
3. 免审分类提交后直接发布，审批日志备注含"免审"。
4. 定时发布在 1 分钟内自动生效（定时任务日志可查）。
5. 发布后 `ann_receipt` 按可见范围生成目标行数，`target_count` 与实际行数一致。
6. 学生标记已读后，未读数与部门排行同步变化。
7. 催办会给未读用户生成站内信，`urge_count` 自增。
8. 敏感词命中 `BLOCK` 时提交被拒，错误信息可读。
9. 编辑公告生成版本快照，`version` 字段自增。
10. 统计概览接口有 Redis 缓存且 60 秒过期。
11. 所有写操作在 `sys_operation_log` 有记录，含 IP 与耗时。
12. 附件上传限制白名单与 20MB 上限，非白名单类型被拒绝。
